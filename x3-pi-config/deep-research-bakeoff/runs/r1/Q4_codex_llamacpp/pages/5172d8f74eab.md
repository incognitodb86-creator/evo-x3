# Codex Local Model Switching
Use local or self-hosted models with OpenAI Codex CLI and the Codex desktop app without constantly hand-editing ~/.codex/config.toml .
This repo is a practical guide plus templates for four setups:
- Official OSS mode for Codex CLI with Ollama or LM Studio.
- CLI profile mode for any OpenAI-compatible provider.
- Complete config switching for Codex CLI, IDE, and App.
- Separate CODEX_HOME mode for advanced isolation.
For most desktop users who want quick GUI switching, complete config switching is the most practical option:
- a normal GPT-backed Codex app
- a local/self-hosted Codex app profile for llama.cpp, Ollama, LM Studio, vLLM, or a router
## Why this repo exists
Codex now supports local/open-source providers, but the ergonomics differ by surface:
Surface
Good switching method
Notes
Codex CLI
--oss , --local-provider , or --profile
Official and clean.
Codex IDE extension
Uses the shared config.toml ; model selector can help for common settings
Advanced provider defaults still live in config.
Codex desktop app
Reads config.toml ; no public --profile picker in the GUI
Use complete config switching or a stable local router endpoint.
Project-local .codex/config.toml is not the right place to redirect model providers. Official docs say project config ignores provider/auth redirection keys such as model_provider , model_providers , openai_base_url , and profile . Put provider definitions in user-level config, an alternate CODEX_HOME , or a complete user config selected by a switcher.
## Official docs this follows
- Advanced config and OSS mode: https://developers.openai.com/codex/config-advanced#oss-mode-local-providers
- Config basics and precedence: https://developers.openai.com/codex/config-basic
- CLI reference: https://developers.openai.com/codex/cli/reference
- Codex models and custom providers: https://developers.openai.com/codex/models
- Codex app settings: https://developers.openai.com/codex/app/settings
## Recommended architecture
For public tutorials and reproducible setups, avoid making Codex point directly at a model-specific endpoint everywhere.
Prefer this:
Codex CLI / IDE / GUI
|
v
stable provider alias
|
v
complete config switcher or local router
|
v
Ollama / LM Studio / llama.cpp / vLLM / cloud provider
That gives you two clean layers:
- Codex config decides which environment is active.
- Your local provider/router decides which model is behind that environment.
## Option A: Official OSS mode for CLI
If you use Ollama or LM Studio, start here.
Add this to ~/.codex/config.toml :
oss_provider = " ollama " # or "lmstudio"
Run:
codex --oss
Or specify a provider explicitly:
codex --oss --local-provider ollama
This is the cleanest CLI-only path. It does not solve GUI/App quick switching by itself.
## Option B: CLI profile for a local/custom provider
Keep provider definitions in your normal ~/.codex/config.toml :
[ model_providers . llama_cpp_qwen ]
name = " llama.cpp Qwen "
base_url = " http://192.168.1.66:8080/v1 "
requires_openai_auth = false
Create a CLI profile file:
# ~/.codex/qwen-local.config.toml
model = " Qwen3.6-27B-Uncensored-HauhauCS-Balanced-MTP-Q5_K_P.gguf "
model_provider = " llama_cpp_qwen "
model_context_window = 131072
model_auto_compact_token_limit = 120000
model_reasoning_effort = " minimal "
model_reasoning_summary = " none "
model_supports_reasoning_summaries = false
Run:
codex --profile qwen-local
For non-interactive tests:
codex exec --profile qwen-local --sandbox read-only --skip-git-repo-check " 只回答 OK。 "
This is the best official-style setup for CLI. It does not automatically affect the Codex desktop app.
## Option C: Complete config switching for GUI/App
This is the most reliable method when you need the Codex desktop app and CLI to switch together.
Instead of editing individual keys in ~/.codex/config.toml , keep complete config files:
~/.codex/model-configs/gpt.toml
~/.codex/model-configs/qwen.toml
~/.codex/model-configs/ollama.toml
Then point ~/.codex/config.toml at the active one.
This avoids fragile search/replace scripts. Each model gets a full, readable config.
### 1. Install the switcher
install -m 755 scripts/codex-model ~ /.local/bin/codex-model
### 2. Create config files
Create:
mkdir -p ~ /.codex/model-configs
cp ~ /.codex/config.toml ~ /.codex/model-configs/gpt.toml
cp templates/codex-home-local/config.toml ~ /.codex/model-configs/qwen.toml
Edit ~/.codex/model-configs/qwen.toml for your host/model.
For the example Qwen + llama.cpp server in this repo:
model = " Qwen3.6-27B-Uncensored-HauhauCS-Balanced-MTP-Q5_K_P.gguf "
model_provider = " llama_cpp_qwen "
model_context_window = 131072
model_auto_compact_token_limit = 120000
model_reasoning_effort = " minimal "
model_reasoning_summary = " none "
model_supports_reasoning_summaries = false
[ model_providers . llama_cpp_qwen ]
name = " llama.cpp Qwen "
base_url = " http://192.168.1.66:8080/v1 "
requires_openai_auth = false
### 3. Switch models
codex-model use qwen
codex-model use gpt
codex-model current
codex-model list
After switching, restart the Codex app or open a new thread.
This works for:
- Codex CLI
- Codex IDE extension
- Codex desktop app
because all surfaces read the same active ~/.codex/config.toml .
### Why not just use separate CODEX_HOME ?
Separate CODEX_HOME is clean in theory, but it can surprise users when their working directory itself contains a .codex/config.toml .
For example, if your work root is ~/project and it contains ~/project/.codex/config.toml , Codex may load that project config above the alternate CODEX_HOME user config. A complete config switcher avoids that confusion because the active user config and any project config are the same file in typical single-user setups.
## Option D: Separate CODEX_HOME for advanced isolation
Use this when you want totally separate Codex state, history, caches, and config:
~/.codex -> normal GPT-backed Codex
~/.codex-qwen -> local Qwen-backed Codex
~/.codex-ollama -> local Ollama-backed Codex
Create a local Codex home:
mkdir -p ~ /.codex-qwen
cp templates/codex-home-local/config.toml ~ /.codex-qwen/config.toml
Launch CLI with that home:
CODEX_HOME= " $HOME /.codex-qwen " codex
Launch Codex App on macOS:
scripts/launch-codex-app-with-home.sh " $HOME /.codex-qwen "
If Codex App is already open, quit it first so the new process gets the new environment.
### Why these reasoning settings?
These three keys are conservative defaults for local/OpenAI-compatible providers that are not first-party Codex models:
model_reasoning_effort = " minimal "
model_reasoning_summary = " none "
model_supports_reasoning_summaries = false
They are not required for every local model, but they avoid common compatibility problems.
model_reasoning_effort controls the requested reasoning effort. Official values are:
minimal | low | medium | high | xhigh
For GPT-5-class OpenAI models, higher values can improve difficult tasks. For local providers, the setting may be ignored, partially mapped, or converted into extra request fields the server does not understand. Use minimal first, then raise it only after basic requests and tool use are stable.
model_reasoning_summary controls whether Codex asks for reasoning summaries. Official values are:
auto | concise | detailed | none
For local models, none is safest. Many OpenAI-compatible servers do not implement Codex/OpenAI reasoning-summary fields exactly. Asking for summaries can waste tokens, produce empty reasoning blocks, or expose incompatibilities in the provider.
model_supports_reasoning_summaries forces Codex's belief about whether the active model supports reasoning summaries:
model_supports_reasoning_summaries = false
Use false for llama.cpp, Ollama, LM Studio, and similar local providers unless you have verified that your server implements the relevant Responses API reasoning-summary behavior. This does not mean the model cannot "think" internally or emit <think> text. It only says Codex should not expect first-party reasoning-summary support from the provider.
After the local setup works, advanced users can experiment:
model_reasoning_effort = " low " # or medium/high/xhigh
model_reasoning_summary = " auto " # or concise/detailed
model_supports_reasoning_summaries = true
Change one key at a time and test with codex exec before using the GUI.
## Option E: Stable local router endpoint
For the cleanest long-term setup, point Codex at a stable local router:
model = " codex-local "
model_provider = " local_router "
[ model_providers . local_router ]
name = " Local model router "
base_url = " http://127.0.0.1:4141/v1 "
requires_openai_auth = false
Then switch the backend in the router, not in Codex:
codex-local -> llama.cpp Qwen
codex-local -> Ollama qwen3-coder
codex-local -> LM Studio model
codex-local -> cloud fallback
Use LiteLLM, a small internal proxy, or your own gateway. The important design choice is that Codex sees one stable provider and one stable model alias.
This is better for teams and public tutorials because it avoids explaining Codex GUI profile limitations to every user.
## llama.cpp notes for Codex
Recent Codex versions use the Responses API path for custom providers. wire_api = "chat" is no longer supported in current Codex CLI builds.
llama.cpp has OpenAI-compatible endpoints, but model chat templates can still matter. With Qwen GGUF templates, Codex requests may fail with an error like:
System message must be at the beginning
For the Qwen3.6 27B GGUF setup tested here, using the built-in chatml template made Codex requests work:
--jinja \
--chat-template chatml
That is a compatibility tradeoff:
- Good for Codex CLI/App.
- Less ideal if your normal chat UI expects the model's native thinking template.
If you need both, run two llama.cpp servers on different ports:
8080 -> Codex-compatible chatml server
8081 -> native Qwen thinking/chat server
## Example llama.cpp command
See:
- templates/llama.cpp/qwen-codex-chatml.sh
- templates/llama.cpp/qwen-native-thinking.sh
The Codex-compatible command uses:
--jinja \
--chat-template chatml
The native-thinking command uses:
--reasoning on \
--reasoning-format deepseek-legacy
## Quick verification
Check server health:
curl http://192.168.1.66:8080/health
Check Codex CLI:
codex-model use qwen
codex exec --sandbox read-only --skip-git-repo-check " 只回答 OK。 "
Expected output includes:
model: Qwen3.6-27B-Uncensored-HauhauCS-Balanced-MTP-Q5_K_P.gguf
provider: llama_cpp_qwen
## Troubleshooting
### GUI still uses GPT
You probably switched config after the app/thread had already started.
Use:
codex-model use qwen
Then quit/reopen Codex App or start a new thread.
### CLI profile works, GUI does not
That is expected. --profile is a CLI flag. The app does not expose a public profile picker in the same way.
Use complete config switching with codex-model , separate CODEX_HOME directories, or a stable local router endpoint.
### llama.cpp returns template errors
Try the Codex-compatible server template:
--jinja --chat-template chatml
### Tool warnings from llama.cpp
Codex may send Responses-style tool metadata. Some local servers skip unsupported tool types. This is another reason to use a router or compatibility layer for production-like use.
### Context compaction
Codex still manages its own thread context and compaction behavior. Your local model's context window still matters. Set:
model_context_window = 131072
model_auto_compact_token_limit = 120000
for a 128k local model.
## Security notes
- Do not commit auth.json , API keys, or private CODEX_HOME state.
- Keep provider credentials in environment variables or local-only config.
- If you copy a Codex home, inspect it before sharing.
