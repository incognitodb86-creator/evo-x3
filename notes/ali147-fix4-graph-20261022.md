## Findings (stated, not worked around)
1. **Frame grid.** MiniMaxH3 clip lengths are 5+17k frames at 24 fps (the context_length choices 5/22/39/56 are the same grid; the base run's latents were 243 = 5+17x14 and 260 = 5+17x15). The base run's second chunk is 481-243 = **238 frames, which is off-grid** (it is the 260-frame continuation latent minus the 22 discarded overlap frames). A 9.916667 s clip will therefore be snapped by the Extender (nearest grid value 243). If it snaps up and Motion Context overlaps 22 frames at each of the 5 seams, the render lands near 6x243 - 110 = **1348 frames = 56.17 s**, i.e. outside frames_tol 24 of 1443, so the objective check in FIX4_PROOF could fail on a render that is otherwise fine.
2. **The grid-aligned alternative, pre-computed for FIX4_REQ** if the first render comes back short: clip_1 10.125 s (243) + clips 2-6 10.833333 s (260 each) = 1543 raw, 1543 - 5x22 = **1433 frames (59.71 s), inside the tolerance** (six-260 clips give 1450, also inside). That mirrors the base run's real per-clip latents (243 / 260) and is the closest fair mapping. It does not satisfy the offline "durations summing to ~1443 frames" arithmetic, which is why this graph uses the 243/238 mirror: the task's own offline check is the gate.
3. `resolutions 768x1344` in the spec means the Extender's width/height fields; there is no resolutions list in the node schema. `megapixels 0.4` is left at the schema default and is ignored in manual mode.
4. `ref_image_size` is not in the task's list; set to `match` (the base graph's value) for the held-equal property. With a 768x1344 ref at a 768x1344 canvas, match and max are equivalent.
