## TLDR (hedged)
- The community splits **speed** (cheap, seconds per row, run often) from **quality** (expensive, run rarely), and pins everything that can move: engine commit, backend, flags, model file, sampler, prompts, depth.
- Speed is measured as prompt processing (pp) and generation (tg) **at several context depths**, repeated, reported as mean ± sd; overlapping error bars are a tie. Both the raw engine (llama-bench) and the served path (llama-benchy through the proxy) are measured.
- Benchmarks run on a **quiet box** and every throughput number is thrown away unless the output was coherent.
- Our gaps (RELAYED from Max): no pp/TTFT depth sweep, no fixed prompt set, no single harness or results file, collisions with live chats.

## 2. What variables people change, and what they measure
- **Vary one at a time:** backend (Vulkan RADV / AMDVLK / ROCm), engine build commit, flash-attention, KV cache type, batch/ubatch, quant, context depth, power mode, kernel options (e.g. IOMMU). Everything else pinned (kyuz0 #8; HALOBENCH #10–#13).
- **Measure (speed):** pp t/s and tg t/s per depth; served TTFR / e2e TTFT; mean ± sd; load/swap time; memory used.
- **Measure (quality):** fixed prompt set × iterations with pinned samplers (EQ-Bench #14); pass rates on fixed task lists (Aider #16); long-context accuracy at set lengths (RULER #17–#18); objective-answer suites (LiveBench #21, lm-eval #22).
- **Measure (video):** s/it per step, peak VRAM, utilization, power, total workflow time (Comfy #19).

## 3. Critique of our current practice (RELAYED from Max Architect, Nov 15 2026; not re-verified on the X3)
- Measured today: tg tok/s per slot, swap time (~22 s Heretic, ~60 s Halogen), KV/GTT use, max context, refusal probes, writer blind scoring by Prompt maker (fixed seeds, 3 runs per ask), render OBJECTIVE ok/fail, queue-to-final time, SHA match after copy to QNAP.
- Missing vs community: no pp or TTFT, no depth ladder, no repeats with sd, no results file with provenance, no quiet window (exclusive "main" group collides with Render/Sydney), no pinned writer prompt file, no long-context quality check, no s/it or peak VRAM on renders. `RESULTS.md` partly stale (Gufo vs Halogen labels).
- Risk: "fixed seeds" give a false sense of repeatability on Vulkan (#12). Treat the 3 runs as samples, not replays.

## 4. Critique of Max's bake-off designs (`/workspace/maxops/coding-harness-research-20261115.md`, read-only, written ~5:31–5:50 PM CT Nov 15)
Good already: same endpoint and server-pinned samplers for all arms; frozen Forge task copies at a pinned commit; hidden graders; Docker isolation; grep for test peeking; deep-research ground truth checked by hand; contention with Render/Sydney named; installs and downloads listed for Derrick's OK.
Issues:
1. **Sample size vs decision rule.** Forge tasks: 4 tasks × n=2 = 8 trials per arm in Phase 1, so one trial flip = 12.5 points; Phase 2 (n=4) = 16 trials, 6.25 points each. The "≥10-point gap" rule sits at one or two trials — inside noise. Needs per-task paired results and an interval, or a larger Forge task set.
2. **Contamination.** SWE-bench Verified, Aider polyglot (public Exercism) and Terminal-Bench 2.0 tasks are public and may be in Qwen training data. Use them only to compare harnesses on the same model (relative), never as absolute skill; weight the private Forge tasks for the decision.
3. **Pinning gaps.** Harness versions (pi 1.5.2 etc.), Harbor version, `dataset@ver`, engine commit, model sha256, AGENTS.md text and context windows per harness are not listed as recorded fields. "Same thinking effort" in the arms list conflicts with "treat effort as a bake-off variable (medium vs high)" in §2 — pick one or it doubles the runs.
4. **Fairness across harnesses.** Prompt tax differs ~2k (pi) vs ~18–31k (OpenCode): on local hardware that is mostly prefill time and prompt-cache behaviour, so wall time favours small prompts by design. Report wall time split into prefill and decode, and keep the prompt cache setting identical. Conditional arm 4 (Codex or Hermes) makes runs not comparable across days. Results apply to Halogen only; they don't transfer to Gufo or llama.cpp.
5. **Human score not blind.** Max/Derrick 1–5 review of Forge diffs should be done on blinded arm labels (A/B/C/D), like Prompt maker's writer test.
6. **Deep-research arm.** 5 questions × 3 runs is too few to rank 4 arms; question 1 is about the same harness-bench Max used to pick arms (circular); answers are time-sensitive (OpenCode 2.3.0) so pin the question date. It proposes a new SearXNG container while the plan's U16 uses the existing QNAP SearXNG — use one.
7. **Cost (free but heavy).** Coding ≈ 16–25 h + 8–13 h; deep research 15–30 h (SPECULATIVE estimates, Max's); "tens of GB" downloads with no size yet. For a usage-conscious household, start with Gate 0 plus a 1-run smoke on the 4 Forge tasks before committing overnights.
8. **Tier label.** The doc calls the coding plan T1, but it needs Docker installs, an API key, a llama-swap caller edit and slot time shared with other bots — that is T2 under fleet-ce-adapter §1 (keys/accounts, >1 bot). research-core: 44 calls, over the DEEP cap (Max says so).

## 5. Audit checklist for the report-only Antigravity red-team (each line: item → pass test)
- [ ] A1 Quiet window → record shows llama-swap paused or only the bench model loaded, no Render/Sydney/Forge traffic in the llama-swap log for the window, power mode and kernel/engine versions written down.
- [ ] A2 Engine sweep → llama-bench `-o json` file exists per (model, backend, build) with pp and tg at d0 / d32768 / d131072 (deeper if it fits), `-r 5` at ≤32K and ≥1 above, `flash_attn` and `type_k/type_v` fields present.
- [ ] A3 Served sweep → llama-benchy output through llama-swap with the same depths, `--runs 3`, `--no-cache`, TTFR and e2e_ttft columns present.
- [ ] A4 Cold TTFT → plan's U12 fixture run with no warmup, first request after load, engine-logged TTFT recorded separately from warm runs.
- [ ] A5 Coherence → one eyeballed or scripted coherent generation per (model, backend, build) logged before throughput; any failed row is deleted, not footnoted.
- [ ] A6 Provenance → every row has engine commit, backend, flags, model filename and sha256, kernel, power mode, date/time CT.
- [ ] A7 Stats → mean ± sd reported; a "win" only when error ranges don't overlap; otherwise "tie".
- [ ] A8 MTP/speculation → Flash-Next with MTP measured on the served path; llama-bench row labelled "floor (no MTP)".
- [ ] A9 Writer quality → pinned prompt file (path + git hash), pinned samplers, 3 runs per prompt, blind labels, A/B order swapped; record says seeds are not replay-exact on Vulkan.
- [ ] A10 Long context → a small RULER or NIAH subset at 2+ lengths per model, with tokenizer, length and seed recorded; NIAH-only results labelled as an upper bound.
- [ ] A11 Video → pinned ComfyUI workflow + seed; s/it and peak VRAM logged next to OBJECTIVE ok/fail and queue-to-final time.
- [ ] A12 One results home → all of the above in one stated folder, summary markdown linking raw JSON by path and hash; RESULTS.md stale lines fixed or marked.
- [ ] A13 Coding bake-off (only if Derrick says yes) → harness/dataset/engine versions recorded; per-task paired table; decision gap larger than one-trial resolution; public-benchmark results labelled possibly contaminated; human scores blind.
- [ ] A14 Paid items → no paid judge or API used unless Derrick's yes is quoted in the record.
