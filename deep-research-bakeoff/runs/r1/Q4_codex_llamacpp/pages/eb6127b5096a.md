# Codex Local LLM Setup: Ollama, LM Studio, llama.cpp and vLLM (2026)
How to run OpenAI's Codex on a model served from your own hardware: codex --oss with Ollama or LM Studio, config.toml providers for llama.cpp and vLLM, which Codex surfaces accept local models, the Responses API requirement behind most failures, context and model choice, and the settings that keep code on the machine. Checked against Codex CLI 0.166.0 and OpenAI's documentation on 4 November 2026.

To run Codex on a local LLM, start Ollama or LM Studio and launch the CLI with codex --oss, which defaults to OpenAI's open-weight gpt-oss-20b, or add a provider to ~/.codex/config.toml for llama.cpp's llama-server or vLLM. Whatever the server, it must speak OpenAI's Responses API, because Codex no longer accepts Chat Completions providers, and the model needs reliable tool calling and at least 64K tokens of context.
Codex is OpenAI’s coding agent. The CLI is open source under Apache-2.0 in the openai/codex repository and runs on your machine; the IDE extension and the Codex mode of the ChatGPT desktop app share its configuration file. Local models work, but not on every surface, and not with every server that calls itself OpenAI-compatible.
Commands and keys below were checked on 4 November 2026 against Codex CLI 0.166.0, released on 29 October, OpenAI’s Codex documentation, the openai/codex source code, and the Codex pages of Ollama and LM Studio. Which model to run is a separate question, covered in our shortlist of open-weight coding models . The same exercise for other agents is in our Claude Code walkthrough for local models and our OpenCode configuration guide .
## What works locally in Codex, and what does not
Surface Local model route Notes
Codex CLI --oss with Ollama or LM Studio, or a custom provider in config.toml No sign-in screen when the provider needs no OpenAI authentication
IDE extension (VS Code, Cursor, Windsurf) The shared config.toml , so a default model_provider carries over --oss is a command-line flag, so set the provider and model in the file
ChatGPT desktop app, Codex mode Ollama’s ChatGPT integration, Ollama 0.34.0 or newer Up to five models; chat and voice stay on ChatGPT; ChatGPT sign-in still required

The CLI’s behaviour is confirmed in its source: the login screen appears only for providers that require OpenAI authentication, and the built-in Ollama and LM Studio providers do not. OpenAI’s authentication page also documents a no-authentication option for local custom providers, which leaves out env_key and every other credential setting.
A local model does not make Codex fully offline. Installation and the start-up update check need the network, and Codex sends anonymous usage metrics to OpenAI unless you switch them off. Web search is a hosted tool run by whichever provider receives the request; Ollama’s Codex page says searches sent through its profile go to Ollama’s search service, which needs ollama signin . /feedback uploads logs when you use it, and any MCP server you add makes its own connections. The switches for each are in the sandbox section below.
## The Responses API requirement
Codex talks to model providers only through OpenAI’s Responses API. In the configuration reference, responses is the sole accepted value of wire_api , and an old wire_api = "chat" entry now stops Codex with an error telling you to switch. The retired ollama-chat provider fails the same way. OpenAI announced the deprecation in December 2025 and scheduled removal for February 2026, which is why older tutorials built on Chat Completions no longer work.
Server Responses endpoint Default port Watch for
Ollama /v1/responses since 0.13.3; Codex requires 0.13.4 or newer 11434 Stateless requests only
LM Studio /v1/responses , including stateful follow-ups 1234 The model key must match LM Studio’s identifier
llama.cpp llama-server /v1/responses , converted internally to Chat Completions 9931 in current builds Pass --port to match your config
vLLM /v1/responses 8000 Tool calls need --enable-auto-tool-choice and --tool-call-parser
## Codex with Ollama
First give the model room. Ollama chooses a default window from available VRAM, 4K tokens below 24 GiB and 32K up to 48 GiB, while its Codex page asks for at least 64K:
OLLAMA_CONTEXT_LENGTH = 65536 ollama serve
The quickest setup is Ollama’s launcher, which refreshes Ollama’s model catalogue for Codex and starts it with a dedicated profile. Inside Codex, /model switches between your installed models that support tools; --config configures without starting and --restore removes the profile and catalogue again:
ollama launch codex
Without the launcher, the --oss flag connects a single run to Ollama. Codex defaults to gpt-oss:20b and pulls whatever model you name if it is missing:
codex --oss
codex --oss -m qwen3-coder:30b
Tags ending in -cloud , such as gpt-oss:120b-cloud , run on Ollama’s servers rather than yours. For a permanent setup, add oss_provider = "ollama" to ~/.codex/config.toml , or keep a profile file next to it. Since Codex 0.134.0, profiles live in their own files, ~/.codex/<name>.config.toml , selected with --profile <name> :
# ~/.codex/ollama.config.toml
model = "gpt-oss:20b"
model_provider = "ollama-local"
model_context_window = 65536
[ model_providers . ollama-local ]
name = "Ollama"
base_url = "http://localhost:11434/v1"
wire_api = "responses"
Start it with codex --profile ollama . Custom provider IDs must avoid reserved built-in names such as openai , ollama and lmstudio . Check the context the server actually loaded with ollama ps while Codex works.
## Codex with LM Studio
LM Studio serves Codex through its /v1/responses route on port 1234:
lms server start --port 1234
lms get openai/gpt-oss-20b
lms load openai/gpt-oss-20b --context-length 65536
codex --oss --local-provider lmstudio
Without -m , Codex downloads openai/gpt-oss-20b through LM Studio if it is missing and loads it in the background. Pass -m with any model key LM Studio lists to use something else. LM Studio’s own guide recommends more than about 25K tokens of context; 64K leaves more room for tool output.
In config.toml, LM Studio can be set up two ways. oss_provider = "lmstudio" makes codex --oss choose LM Studio without asking, and a profile file pins a model:
# ~/.codex/lmstudio.config.toml
model = "qwen/qwen3-coder-30b"
model_provider = "lmstudio-local"
model_context_window = 65536
[ model_providers . lmstudio-local ]
name = "LM Studio"
base_url = "http://127.0.0.1:1234/v1"
wire_api = "responses"
We found no LM Studio documentation for the Codex mode of the ChatGPT desktop app as of 4 November 2026; Ollama’s integration, below, is the documented route there.
## Codex with llama.cpp and vLLM through config.toml
Any other server is a custom provider. For llama.cpp, start llama-server with an explicit port, because current builds listen on 9931 by default, and an alias that becomes the model name:
llama-server -hf ggml-org/gpt-oss-20b-GGUF --alias gpt-oss-20b \
--host 127.0.0.1 --port 8080 -c 65536 --jinja
Then describe it in ~/.codex/config.toml or a profile file:
model = "gpt-oss-20b"
model_provider = "llamacpp"
model_context_window = 65536
[ model_providers . llamacpp ]
name = "llama.cpp"
base_url = "http://127.0.0.1:8080/v1"
wire_api = "responses"
Keep model_context_window at or below the server’s -c value, so that Codex compacts history before the server runs out of room. For vLLM, use the same table with base_url = "http://127.0.0.1:8000/v1" , and start the server with --enable-auto-tool-choice and the --tool-call-parser that matches your model, since tool calling is off by default. For several developers sharing one GPU server, our comparison of vLLM, Ollama and llama.cpp covers the trade-offs. The same provider table can also point at a gateway instead of a single server; our look at the OmniRoute gateway covers one open-source option.
Put provider settings in your user-level configuration. Codex ignores model_provider and model_providers in a project’s .codex/config.toml and prints a warning at start-up.
## Local models in the Codex app and the VS Code extension
### VS Code, Cursor and Windsurf
The Codex IDE extension keeps editor options under chatgpt.* settings but reads agent behaviour, including the model and provider, from the same config.toml as the CLI; Codex Settings → Open config.toml opens the file. Because --oss and --profile are command-line flags, put the provider table and the model , model_provider and model_context_window lines from one of the profiles above into the base file. That makes the local model the default for the CLI too.
On Windows, the chatgpt.runCodexInWindowsSubsystemForLinux setting runs Codex inside WSL2. If Ollama or LM Studio runs on the Windows side, localhost inside WSL2 does not reach it under the default NAT networking, so use the host’s address or Microsoft’s mirrored networking mode.
### The Codex app in ChatGPT Desktop
Ollama documents the route for the desktop app. With Ollama 0.34.0 or newer, open the Ollama app, select Apps , switch ChatGPT (Desktop) on and follow the prompts, which may restart ChatGPT. Under Ollama’s Settings → Apps → ChatGPT you then choose up to five local or cloud models, and they appear in Codex’s model picker beside OpenAI’s.
Only requests made with an Ollama model go to Ollama. Chat and voice keep their usual ChatGPT connection, Codex still manages the sessions, and web search with an Ollama model uses Ollama’s search service, limited to three calls per response. Switching the integration off restores ChatGPT’s previous connection settings.
## Choosing a local model for Codex
Codex’s own defaults point at OpenAI’s open-weight gpt-oss models. Both are Apache 2.0 mixture-of-experts models shipped in MXFP4, with a 128K window: gpt-oss-20b has 21B parameters with 3.6B active, and gpt-oss-120b has 117B with 5.1B active. Ollama’s library also lists Qwen models with tool support.

gpt-oss-120b gpt-oss:120b , 65 GB 64.9 GB at 32K context, 68.5 GB at 131K
Qwen3-Coder-30B-A3B qwen3-coder:30b , 19 GB Not measured in that guide

## Context, tool calling and common errors
Codex sends a long system prompt and tool definitions with every turn, then file contents and command output, so a 4K or 8K window fills almost at once. Symptoms include tool calls that loop, half-finished edits and instructions the model seems to forget. Raise the server’s context first, then set model_context_window to match.
The errors you are most likely to meet:
- wire_api = "chat" is no longer supported. Change the provider to wire_api = "responses" and make sure the server has a /v1/responses route.
- ollama-chat is no longer supported. Replace it with ollama in model_provider , oss_provider or --local-provider .
- Ollama is too old. Codex’s version check names the minimum, Ollama 0.13.4; upgrade the server.
- does not support tools . Ollama refuses tool calls for models without tool support; pick a model whose library page lists tools.
- codex exec exits at once with --oss . Non-interactive runs do not prompt for a provider, so pass --local-provider or set oss_provider .
- A profile seems ignored. From Codex 0.134.0, --profile no longer reads [profiles.<name>] tables in config.toml ; move the settings into ~/.codex/<name>.config.toml .
codex doctor --network-only , added in 0.166.0, checks configuration and connectivity when the server cannot be reached at all.
## Sandbox, approvals and keeping code on the machine
The sandbox works the same with a local model as with OpenAI’s. In a Git repository Codex suggests its Auto preset, workspace-write with on-request approvals; outside version control it suggests read-only . In workspace-write , commands can edit the workspace but have no network access unless you enable it, and .git , .agents , .codex and .aws stay read-only. Enforcement comes from the operating system: Seatbelt on macOS, bubblewrap with seccomp on Linux and WSL2, and the MXC sandbox on Windows, with older elevated and unelevated implementations as fallbacks.
approval_policy now accepts on-request , never or a granular table; the old untrusted policy is retired. --dangerously-bypass-approvals-and-sandbox , alias --yolo , removes both layers and belongs only inside an environment that is already isolated. If bubblewrap cannot start inside a Docker container, OpenAI’s guidance is to make the container the boundary and run Codex with danger-full-access there. Our guide to isolating agents that execute code covers containers and microVMs.
To keep a local setup quiet on the network, add these keys to ~/.codex/config.toml :
web_search = "disabled"
check_for_update_on_startup = false
[ analytics ]
enabled = false
[ feedback ]
enabled = false
OpenTelemetry export is off unless you configure an exporter. Confirm the result with egress monitoring, because MCP servers and plugins have their own network behaviour.

## Frequently asked questions
Can Codex use a local LLM?
Yes. The Codex CLI runs local models with the --oss flag, which talks to Ollama or LM Studio on the same machine, or through a custom provider in ~/.codex/config.toml pointing at any server that speaks OpenAI's Responses API, such as llama.cpp's llama-server or vLLM. When the provider needs no OpenAI authentication, the CLI skips the sign-in screen. Codex cloud tasks cannot use a local model. How do I set up Codex with Ollama?
Install Ollama 0.13.4 or newer, raise its context to at least 64K tokens, for example with OLLAMA_CONTEXT_LENGTH=65536 ollama serve, and run ollama launch codex, which creates a dedicated Codex profile and model catalogue. Alternatively run codex --oss, which uses gpt-oss:20b unless you pass -m, pulling the model if it is missing. For a permanent default, set oss_provider = "ollama" in ~/.codex/config.toml. How do I use Codex with LM Studio?
Start LM Studio's server on port 1234, for example with lms server start --port 1234, load a model with more context than LM Studio's suggested minimum of about 25K tokens, and run codex --oss --local-provider lmstudio. Without -m, Codex downloads and uses openai/gpt-oss-20b. Set oss_provider = "lmstudio" in ~/.codex/config.toml to make LM Studio the default local provider. LM Studio serves the /v1/responses endpoint that Codex requires. What does codex --oss do?
The --oss flag switches Codex to a local open-source provider, Ollama or LM Studio, chosen with --local-provider or the oss_provider key; if neither is set, the interactive CLI asks and codex exec exits with an error. Codex then checks that the server is reachable, fetches the model if it is missing, and defaults to gpt-oss:20b on Ollama or openai/gpt-oss-20b on LM Studio, without asking you to sign in. Can Codex use llama.cpp?
Yes, through a custom provider. Start llama-server with an explicit --port 8080, an --alias for the model name and a context size such as -c 65536, then add a [model_providers.llamacpp] table to ~/.codex/config.toml with base_url set to http://127.0.0.1:8080/v1 and wire_api set to responses, and point model and model_provider at it. llama-server answers /v1/responses by converting each request to Chat Completions internally. Does the Codex app or VS Code extension work with local models?
Partly. The ChatGPT desktop app, which contains Codex, can show Ollama models in Codex mode through Ollama's own integration, which needs Ollama 0.34.0 or newer and allows up to five models, while chat and voice stay on ChatGPT and the app still needs a ChatGPT sign-in. The Codex IDE extension reads the same config.toml as the CLI, so a default local provider set there applies to it. Codex cloud cannot use local models.
